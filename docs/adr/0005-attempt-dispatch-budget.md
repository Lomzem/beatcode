# Reserve time for cleanup before dispatching contestant work

Per-test limits and the aggregate contestant-runtime bound do not cap compilation and repeated transport overhead. A submission can stay within both limits yet outlive the sandbox's fixed 40-second lifetime. Before dispatching compilation or each test, the controller now requires the entire existing exec deadline to fit within 38 seconds of the create request, measured with a monotonic clock. The remaining 2 seconds cover the adapter's termination-and-poll window. Persisted timestamps and accounting retain their wall clock; a backward wall-clock adjustment cannot extend dispatch admission. The earlier request timestamp is conservative when remote creation precedes its acknowledgement.

If another call cannot fit, the controller records TLE without dispatching it, closes the sandbox scope, and only then publishes. Compilation uses its existing 15-second transport deadline; each test retains its runner limit and existing 3-second transport allowance. `aggregateMs` still measures contestant runtime. Creation, identity verification, lease acknowledgements, compilation and previous exec/stream overhead consume the shared budget. Identity/preflight failures and dispatched transport/trailer failures keep their existing attribution; elapsed time never invents an infrastructure incident or a cleanup receipt. Cleanup failure still retains ownership through the established recovery protocol. The 2-second reserve is a dispatch margin, not a guarantee of successful termination or punctual cloud scheduling.

This deliberately prefers a bounded TLE to losing the runner at hard expiry. Correct work can receive TLE because of host/transport overhead; heterogeneous timing remains an accepted alpha limitation under ADR0001/ADR0003. Reducing test count alone cannot provide a hard bound, and increasing sandbox lifetime would change reservations and cost caps. Accepted-reference calibration still requires all existing 15-second observed-attempt and 7.5-second aggregate margins; this guard does not replace them, concurrency testing or production acceptance.

The execution policy is `staged-input-reference-10s-attempt-budget-v4`, retaining ADR0004's runtime/compile memory semantics and inspected runner binary. Fresh whole-suite controller qualification, immutable environment/version bindings and fresh calibration measurements are required. Prior v1/v2/v3 reports, receipts, failures, decisions and charges remain historical and cannot be relabeled or reused as v4 measurements. No new image build is needed when its source/binary are unchanged. The existing 40-second reservation, fixed campaigns and resource/monetary caps remain unchanged; further cloud work requires an available explicitly approved allocation.
